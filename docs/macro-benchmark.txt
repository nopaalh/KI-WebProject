PENGUKURAN MAKRO LEWAT HTTP - UPLOAD, UNDUH, DAN BACA KTP
=========================================================

Skrip: scripts/macro_benchmark.py (python scripts/macro_benchmark.py <port> 30). Backend `main` 57d06b2 dibuild lalu
dijalankan terhadap PostgreSQL 16 lokal di Docker (BUKAN database bersama), klien dan server di mesin yang sama
(loopback), satu koneksi per request, tanpa beban lain, Windows, mode debug Gin, Ryzen 5 5600H, 2026-10-27.
Waktu = waktu dinding yang dilihat klien dalam milidetik, mencakup HTTP, JWT, query database, baca/tulis disk, dan
kriptografi. Setiap unduhan dan pembacaan foto dibandingkan dengan SHA-256 aslinya: tidak ada satu pun yang berbeda.

Yang diukur HANYA yang ada di endpoint sekarang: file umum hanya AES1 dan tidak ada pilihan cipher saat dekripsi,
sedangkan baca KTP selalu mendekripsi ketiga cipher. Unduh per cipher (DES/RC4) lewat endpoint belum bisa diukur.

TEMUAN
------
1. HTTP hampir tidak menambah biaya. Unduh 1 MiB acak: 1144 ms di klien vs 1132 ms dilaporkan server (dekripsi AES1) vs
   1162 ms di harness kriptografi murni (ciphertext-analysis.txt). Selisih sekitar 12 ms (sekitar 1%); pada 16 KiB sisa
   biaya tetap sekitar 15 ms. Jadi kecepatan ditentukan cipher, bukan jaringan, JWT, atau database.
2. Upload AES1 sekitar 1,6-1,7 detik per MiB, hampir persis enkripsi + dekripsi verifikasi (1 MiB: 498 + 1132 = 1630 ms
   dari 1738 ms; 4 MiB: 1994 + 4472 = 6466 ms dari 6469 ms). Verifikasi round-trip saat upload menyumbang dua pertiga
   waktu karena dekripsi AES buatan tangan 2,3x lebih lambat dari enkripsinya.
3. Upload KTP (tiga cipher, round-trip ketiganya) sekitar 2,8-3,0 detik per MiB foto: 773 ms (255 KiB), 2980 ms
   (1022 KiB), 11190 ms (4094 KiB). Itu cocok dengan penjumlahan cipher (enkripsi AES 0,50 + DES 0,64 + RC4 0,004 dan
   verifikasi 1,16 + 0,63 + 0,004 = 2,94 detik per MiB). Dengan batas 8 MiB, satu upload tiga cipher kira-kira 22-24 detik.
4. Baca foto KTP sekitar 1,7 detik per MiB (0,57 MB/s), jauh lebih lambat dari unduh file AES (0,87 MB/s), karena setiap
   pembacaan mendekripsi AES, DES, dan RC4 lalu membandingkan hasilnya. Biayanya mengikuti jumlah cipher yang dibaca,
   bukan satu cipher. Baca teks KTP (15 field x 3 cipher) hanya sekitar 28-34 ms dan tidak bergantung ukuran foto.
5. Isi data tidak memengaruhi waktu: 1 MiB acak 1144 ms vs teks 1137 ms. Waktu naik linear: 0,45 MB/s pada 16 KiB
   (biaya tetap), lalu 0,82 / 0,87 / 0,89 MB/s pada 256 KiB / 1 MiB / 4 MiB.
6. Variasi kecil: unduh 1 MiB berkisar 1120-1240 ms (maks 8% di atas median).
7. Alur KTP dan profil berjalan benar di PostgreSQL nyata (create, GET teks, GET foto, SHA-256 foto cocok). Dokumen
   PATIENT_KTP.md sebelumnya mencatat PostgreSQL nyata belum diuji.

PERKIRAAN, BUKAN HASIL UKUR (per cipher, satu MiB)
--------------------------------------------------
Jika endpoint kelak membaca satu cipher saja, dari ciphertext-analysis.txt dekripsi 1 MiB sekitar AES1 1,16 s, DES1 0,63 s,
RC41 0,0035 s ditambah sekitar 12 ms biaya tetap HTTP di atas. Angka itu harus diukur ulang dengan skrip ini setelah
`?algorithm=` ada.

KETERBATASAN
------------
- Klien dan server satu mesin (loopback); bukan latensi jaringan nyata. Satu pengguna, tanpa konkurensi.
- Satu koneksi baru per request, mode debug Gin, satu mesin Windows; angka mutlak tidak berlaku untuk server lain.
- Semua cipher buatan tangan edukasi. Dengan crypto/aes dan crypto/des stdlib angka dan urutannya berbeda jauh.
- Hanya AES untuk file umum; DES dan RC4 lewat endpoint menunggu permintaan 1 dan 2 di BACKEND_HANDOFF.md bagian 12.
